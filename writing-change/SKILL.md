# 从 BRIEF 到四份规格产物

输入：一份 BRIEF（`writing-brief` 的产物）。用户会直接把路径给你。
**变更名就是这个文件的文件名**（去掉 `.md`），不要另起。

写这四份文件**派出去**，不要自己写——它是四份文件加每条任务的验法，纯体力活里最贵的一档。
而且「只读 BRIEF、不读对话」这条约束**只有派出去才是真的**：冷启动的 agent 物理上读不到
你和用户的对话，你做不到。

## 第 1 步：你自己做的三件事（不外包）

1. **读完 BRIEF。** 尤其是「否决了什么 · 为什么」那一列——下游 agent 会把没写进任务书的
   否决重新当好主意提出来，而你是唯一知道它们被否过的人。
2. **找出相关的现有规格。** 先列出项目已有的规格，再拿 BRIEF 里的领域词（表名、模块名、
   指标名）去规格目录 grep 一遍。**命中的全部点名**——凭回忆点名时漏掉的那份往往正是最该
   读的那份，因为你记得住的都是你已经在想的。
3. **判断这次要不要写规格。** 纯重构 / 工具 / 文档类的变更没有新的对外承诺，跳过规格那一份
   （项目怎么声明「跳过」见【项目适配】）。判据只有一条：**它有没有新的对外承诺**，
   不是「改动大不大」。

然后把变更目录建出来。

## 第 2 步：组装任务书，派一个子 agent

通道用哪个由你和用户当时定，**这个 skill 不绑具体通道**——重要的是任务书写了什么，不是谁来跑。
派活机制（任务书要件、白名单、发送命令、收活）见 `orchestrating-agents`；用哪个模型（命令名、
价格）见 `dispatch-dlaude` / `dispatch-glm`。

任务书必须点名的东西（冷启动的 agent 不点名就不读，用全路径）：

- BRIEF 的绝对路径，**并写明「这是唯一的需求出处，不要问对话里有什么」**
- 第 1 步找到的现有规格文件，全路径逐个列出
- **项目里若有生成规格产物的现成流程**（见【项目适配】），点名那份文件让 agent **用 Read
  读它并照做**——不要依赖 Skill 工具，派出去的 agent 未必给了那个权限。这类流程通常由工具
  链随版本生成，所以细节永远以它为准，别在任务书里抄一份。**没有的话**，就按下面第 ① 条的
  职责表自己写四份。
- 下面那三条规矩——**生成流程不知道它们，必须原文写进任务书**

任务书还要划死：不许改产品代码（这一步只产出规划产物）、不许动文档目录、不许动既有规格的
主文件（只写增量）。报告落盘到 scratchpad，要求边做边写。

## 第 3 步：写进任务书的三条规矩（原文照抄）

### ① 四份文件的职责，不许互相复述

| 文件 | 装什么 |
|---|---|
| 提案 | 为什么 + 范围边界 + 非目标。不逐条列 Requirement |
| 规格 | 行为契约，唯一的对外承诺出处。不写类名/库名/实现步骤 |
| 设计 | 怎么落地 + 取舍。不重述 why |
| 任务 | 执行步骤 + 每条的验法 |

操作化成三问，交付时逐条回答：规格里有没有实现细节？设计里有没有重述 why？
提案里有没有逐条列 Requirement？

### ② 每个 Scenario 的标题末尾带验法标签

```
#### Scenario: 查询返回胜率 [@unit]
#### Scenario: 停用后观众立刻失去访问 [@e2e]
```

四选一：`@e2e`（真浏览器走得到）／`@unit`（不变量、纯函数、口径）／`@scan`（扫描器拦的
规则）／`@manual`（要连真实外部系统）。

**写在标题行里**，理由是：标题行往往是规格格式里唯一被严格约束的一行（少一个 `#` 会**静默
失败**），且整块替换某条 Requirement 时，标签跟着块一起搬走，不会掉队。

### ③ 每条任务的验法是一个测试的完整名字

用 ` — verify: ` 分隔，冒号后跟测试全名：

```
- [ ] 2.3 给数量闸门补永久正例 — verify: Web.Tests.DocBudgetScanTests.正例会被抓到
```

例外必须显式标注**并写一句为什么**：`@manual`（要连真实外部系统）／`@deploy`（只能在目标
环境验）／`@doc`（纯文档交付物）／`@new <测试全名>`（本次要新建、此刻还不存在，**过渡态**，
勾上前必须换成真名字）。

**不允许无标签的自然语言验法**——它和「根本没写」在事后长得一模一样。

## 第 4 步：复核，然后问用户要不要扫

自己读一遍四份产物（尤其是第 ① 条那三问，那是内容判断，扫描器做不了），然后**问一句**，
不要自作主张跑：四份产物已落到某某目录，要跑一遍闸门吗？

⚠️ **这一步只跑「验法是不是测试全名」和「规格结构校验」两类。** 「`@e2e` 标签数 == e2e
用例数」那道闸门此刻**必红**——用例要等实现阶段才存在，那个红是对的，不是缺陷。

⚠️ 项目里若没有这些扫描器，明说「这几条规矩此刻无人把守」。**一道写在文档里而不存在的
闸门，比没有闸门更糟。**

## 下一步

规格产物落盘之后，实现走 `/implementing-change`（用户手动调）。
**这个 skill 到此为止**，不要顺手开始实现。

## 项目适配

换项目时**只改这一节**，正文一个字不用动。

| 要什么 | 本项目的值 |
|---|---|
| 规格体系 | OpenSpec（`openspec/`），四份产物是 `proposal.md` / `specs/<capability>/spec.md`（增量）/ `design.md` / `tasks.md` |
| 建变更目录 | `openspec new change <名字>` |
| 列现有规格 | `openspec list --specs`，规格在 `openspec/specs/` |
| 生成流程（让 agent 读它照做） | `.claude/skills/openspec-propose/SKILL.md` |
| 声明「跳过规格」 | 变更目录里的 `.openspec.yaml` 设 `skip_specs: true` |
| 第 4 步跑的闸门 | `dotnet test --filter TaskVerifyScanTests`、`openspec validate --strict` |
| 此刻必红、留到实现阶段的闸门 | `ScenarioTagScanTests` |
