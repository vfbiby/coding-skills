# 当调度者

你不写代码，你决定做什么、判断收回来的东西是不是真的。

**一个只会说「通过」的检查，和一个坏掉的检查，长得一模一样。** 这句话是整个 skill 的轴。所有招式都在回答同一个问题：**这个绿，是真的吗？**

## 只有四件事是你的

其余一律派出去——**包括应用审查发现**。「顺手改一下」是最容易滑坡的地方，那也是改代码。

1. **写 spec、定契约、拆任务。** 决定做什么。
2. **记录决定与坑**（ADR / 坑库 / 未决问题——具体落在哪个文件由各项目定）。别人写的记录会漏掉「为什么」，而半年后只有「为什么」还有用。
3. **复核。** 亲手跑一遍，**自己换一种注入**。见下面「复核」一节——这是唯一不能派的东西。
4. **提交 git。** 你是唯一看过全局的人。

## 循环

```
写 spec ─► 派实现 ─► 你复核 ─► 派审查 ─► 派修复 ─► 你复核 ─► 提交
                         │                              │
                         └──── 换一种注入 ──────────────┘
```

审查 agent **不给构建工具**（见下面「白名单」），于是实现与审查可以真并行——它照样能读代码、回源核对、写报告。

## 复核：唯一不能派的部分

报告说全绿，你自己跑。报告说注入实验红在第 N 条，**你换一种注入自己验**。

**别重复实现者做过的注入。** 它做过的那两种，它已经确保会红了。你要找的是它**没想到**的那一种——通常就是你读代码时起疑却说不清的地方。

判据：**你亲手跑出来的输出**与报告一致，且关键断言在**你自己的注入**下红在预期那一条上。只读报告不算复核。

### 注入的三条纪律

1. **落在真正被执行的代码上。** 注入进注释、进死分支、进没被引用的重载——测试不红不代表防线失效，代表实验做错了。
2. **负面断言排在正面断言前面。** 排在后面会被前面的等值断言短路掉，注入「看起来验过了」而其实没执行到。
3. **一次只坏一处。** 同时坏两处时，你分不清是哪条防线在响。

### 从注入结果反推的四种情形

| 现象 | 含义 |
|---|---|
| 只红在预期那一条 | 防线是活的，且**范围恰好** |
| 红了一片 | 防线活着，但耦合过紧——诊断时会追错方向，记下来 |
| 一条没红 | **假绿**。要么防线是空的，要么你的注入没落到执行路径上——先排除后者 |
| 单跑绿、并行红 | **假红**，比没有测试更糟：它训练人「再跑一次就好了」。先怀疑静态可变状态、执行顺序依赖、真实时钟 |

**被杀的 agent 会把注入留在工作树里**（「改坏→跑→改回来」停在「改坏」那步，看起来像一处实现）。没有报告 = 先当作有半截注入没回滚：`git diff` 逐处过，找「删掉一个调用」「true 改 false」这种孤立改动，对着注入靶子核。

**收活不要 `git add -A`。** 另一个 agent 可能正跑着或没复核——会卷进你的提交，一个提交两件事，事后 `reset --soft` 拆。**按路径 add**，或先 `git status` 看清楚。

## 主动去找假绿

绿是默认状态，所以假绿不会来找你。这些形态要主动翻：

**名字大于覆盖。** 「黄金样本」听起来全面，实际只覆盖它碰到的那几个格子。**去数它的断言，不要读它的名字。** 发现名字比覆盖大时，改名或改注释，**不许为了保住名字去加断言凑数**。

**测试数据让两种实现给出同一个答案。** 最常见的形态：验「合并 vs 覆盖」只写两段数据，而人天然会让后一段更极端——于是「取 max」与「取后到的」得到同一个数，那一列的断言什么都没钉住。**写三段，让真值落在中间那段**，两个错误方向就都分叉了。

**期望值与被测实现同源。** 测试从实现读来的常量去断言实现，永远为真。判断标准：举出一个「这么改之前能抓到、改之后抓不到」的具体 bug；举不出来才叫无损失。

**扫描器没有永久正例。** 在测试程序集里放一个**永不被调用**的违规函数，加一条断言证明扫描抓得到它。没有正例，「没扫到违规」这个结论一文不值。正例还要覆盖到**过滤器那一支**——否则过滤器坏掉时两条测试同时绿。

**冷路径符合注释、热路径不符合。** 「保留 3 天」在停止写入的键上完全正确，在每秒都写的键上永不过期。随手验的总是冷的那个。

## 派活

派出去的 agent 是**冷启动**的：它不知道这个仓库、不知道之前几轮做过什么、不会自己去找该读的文件。**需最精细判断的活（协议解码、并发正确性、金额计算）不派给便宜模型，走默认模型的 Agent 工具。** 派活分两半：**任务书写什么**（内容）和**怎么发**（机制）。下文 `<派活命令>` 是占位——用哪个模型的命令，见 `dispatch-dlaude`（DeepSeek）或 `dispatch-glm`（GLM）。

### 任务书写什么

- **第一行写清本场可用工具**（对应下面白名单 bundle）：如「本场有 `Read,Write,Edit,Glob,Grep,Bash(dotnet:*)`」，并提醒「看文件用 `Read`/`Grep`，别用裸 `Bash`；跑测试只能走 `bash <脚本>`」——agent 一审就知道边界，省掉被拒的 turn。
- **点名要读哪几个文件，用全路径**（相关 ADR、坑库条目 `docs/pitfalls/P-<编号>-<slug>.md`、spec、tasks——不点名它就不读）。**点名前先 grep**，拿改动领域词去文档目录搜一遍，命中全点名。**凭回忆点名，漏掉的那份往往正是最该读的那份**——你记得住的都是你已经在想的。
- **写清这轮最容易做错什么、错了会怎样**——不是「实现 X」，是「X 做错不会报错，只会让 Y 看起来更好」。agent 会照着你描述的失败形态去防。
- **报告写进文件，不在流里**。给绝对路径（scratchpad 下 `report-<活名>.md`），要求**边做边写、每节落一次盘**——流是易失的，agent 被杀时报告就没了，磁盘上的半份报告永远比零份强。
- **报告写在测试跑绿之后、收尾之前**（长任务接近上限会被杀，活干完了报告丢了）。
- **每次调试/注入改动做完立刻改回来并重跑确认绿**（有 agent 死在「改坏」和「改回」之间，那处 `throw;` 若跟着提交会打断整个循环，且无测试覆盖）。
- **划死不许碰的**：别的模块、别的任务组、既有测试、文档目录、共用资源（数据库、Redis 逻辑库）。共用资源的约束要**逐字重申**，不能指望它推理出来。
- **注释只许引用能回源核对的出处**（ADR 编号、spec 的 Requirement 名、坑编号 `P-n`、文件全路径）。任务书里的「第 3 组」「6.7」是一次性的，写进注释就是死链。
- **交付要求写成可检查的**——贴真实测试输出（条数）、贴注入失败输出、逐条回答指定问题。「写份报告」换来复述注释，「数出你写了几条断言」换来真数了。

### 怎么发

**派活前先留可回退基线**：已成型的正常提交掉（一次一个）；未跟踪新目录 git 帮不上忙，`cp -r <目录> <scratchpad>/baseline-<名字>/`。没基线，「改回去」变「重新写一遍」→ 又会再派一轮。**撤回/还原/机械替换自己做，不派**——判据是**要不要做判断**，不是体量。**转发报错给执行侧前先自核**「不存在/找不到」——存在性是双方能独立核实的事实。

**探活**：

```bash
zsh -c "source ~/.zshrc >/dev/null 2>&1; <派活命令> -p 'reply with exactly: OK'"
```

**探你这次真要用的那个**（不同模型通道坏不保证同时坏）。通道整体坏（TLS 等）时 `RESULT` 仍报 `success`——判据是响应正文，不是 `subtype`。探不通就自己写。

**发出去**（写到 scratchpad 的 `task.md`，不进仓库）：

```bash
S=<scratchpad 目录>
zsh -c "source ~/.zshrc >/dev/null 2>&1; <派活命令> -p \"\$(cat $S/task.md)\" \
  -n '<活名：如 loginwindow-实现豁免>' \
  --output-format stream-json --verbose --permission-mode acceptEdits \
  --allowedTools '<按活收紧，见白名单>'" 2>&1 \
  | tee "$S/task.log" \
  | grep --line-buffered '^{' | jq -rc --unbuffered 'if .type=="assistant" then (.message.content[]? | if .type=="text" then "TXT "+(.text|.[0:220]) elif .type=="tool_use" then "USE "+.name+" "+((.input.file_path // .input.pattern // .input.command // "")|tostring|.[0:110]) else empty end) elif .type=="result" then "RESULT "+(.subtype//"")+" turns="+((.num_turns//0)|tostring) else empty end'
```

配 `run_in_background: true`。每段挡一个失败：`--output-format stream-json --verbose`（`claude -p` 默认缓冲、跑完才吐；加它还能在杀进程后从日志捞回已完成的调查）；`tee` 分流（stdout 全重定向会让 harness 任务输出为空）；`jq` 投影（一条 NDJSON 几千 token，压成一行、正文截 220、工具调用截 110）；`--permission-mode acceptEdits`（`--dangerously-skip-permissions` 会被 auto 分类器拦）；`-n '<活名>'`（落成会话 JSONL 首行 `custom-title`，否则 `/resume` 里是一串 UUID）。**用 `acceptEdits`，不用 `plan`**：headless 下 `ExitPlanMode` 没有出口，审查 agent 以为自己交付了，整份报告消失。

**等通知**：后台任务跑完自动叫你，去看那个 output 文件（已投影成可读行）。Agent 工具派的子 agent 则不同——output 是完整 JSONL 转录，读它会撑爆上下文，只能等通知。**不要挂 Monitor**（每条事件一次全量 API 调用）。

### 白名单

`--allowedTools` 必须写在命令行上，`.claude/settings.json` 的 `permissions.allow` 对派出去的 agent 无效（workspace 未 trust）。

**用下面三个具名 bundle，整块粘贴，别每次手拼**（手拼会想不全、agent 想用的工具被拒、多绕 turn）：

```
# ① 只读调查（审查、排查、回源核对）——绝不给 Write/Edit
Read,Glob,Grep,Bash(git diff:*),Bash(git status:*),Bash(git log:*),Bash(ls:*),Bash(cat:*),Bash(sed -n:*),Bash(head:*),Bash(tail:*),Bash(wc:*)

# ② 实现（写代码 + 自测）——在 ① 基础上加写与构建
Read,Write,Edit,Glob,Grep,Bash(git diff:*),Bash(git status:*),Bash(ls:*),Bash(cat:*),Bash(sed -n:*),Bash(head:*),Bash(tail:*),Bash(wc:*),Bash(bash:*)  + 构建工具前缀（如 `Bash(dotnet:*)`）

# ③ 审查（= ①，一个字都不加）
```

- `Bash(sed -n:*)` 只放读，`sed -i` 不匹配；② 的 `Bash(bash:*)` 给包装脚本用，但也等于给了完整 shell——所以 ①③ 绝不能加它。
- **给 `Grep` 工具，不给 `Bash(grep:*)`**——后者能让 agent grep shell snapshot，而各派活命令的函数体都在里面，带硬编码的 API token。
- `Bash(xxx:*)` 是**前缀匹配**：`set -a; . ./.env; dotnet test` 不以 `dotnet` 开头会被拒。把 `source .env` 封进脚本、白名单给 `Bash(bash:*)`，任务书写死「跑测试只能用 `bash <脚本路径>`」。收太紧的代价不是报错而是误导（agent 反复 `printenv` 试探，得出错误结论）。
- **审查 agent 不给构建工具**——两个 agent 同时构建抢 `obj/`/`dist/`，两边都坏。任务书写明「构建由主会话跑」，它照样能读代码写报告。
- **「只分读写」这条轴是错的**（`Bash(bash:*)` 一给就是完整 shell，Bash 层切不成读写；`grep` 纯读却必须禁）。真正的轴是**这活要不要写文件、要不要构建**。

### 被杀之后

`RESULT` 行缺失 = 被外部终止（不是崩溃，也不是通道坏——通道坏时 `RESULT` 仍报 success）。**先读磁盘**：

1. `git status --short` —— 落了什么
2. 半成品报告 —— 做到哪、下一个嫌疑是什么
3. `grep -rn "TEMP\|DEBUG" src` —— 调试残留

够不够自己收尾：够就自己收——重派付一次冷启动，已定位到函数级的 bug 自己修比重新交代便宜。日志分不出「被人停」和「被杀」——查 `Console.app` 的 `jetsam` 或 `sysctl vm.swapusage`；分辨不出就别下结论，当成「随时可能发生」来设计任务书。

### 通道坏了

探活不通、或 `RESULT` 报 success 但正文是错误——自己写。派活是省时间的手段，不是前提。

## 派审查的任务书

审查的质量取决于你问了什么。「审查一下」换来的是复述注释。

**首要问题永远是同一个**：还有没有**没还原的注入或半成品**？实现 agent 可能在收尾阶段被强杀，留下改坏的代码和一份说反话的注释。让它逐个文件**把每一处注释声称的不变量拿去对代码核对**。

**把你自己的疑点写成具体问题。** 你读代码时起疑却说不清的地方，正是审查最该去的地方。问「这条测试能不能抓到 X 实现」，不要问「测试写得好吗」。

**要求给行号作依据，不许复述注释。**

**明说「没问题也要说清你是怎么确认的，不要为了显得有产出而编造问题」。** 少了这句，你会收到一堆凑数的低危项。

## 交回验收：必须给一张跨轮次的汇总清单

一件事往往跨很多轮才做完，而「需要人去看一眼」的条目是**沿路掉下来的**——第三轮里你说「这个建议用无痕窗口复测」，第七轮里 agent 留空了一条 tasks，第十轮里你提到「那份文档的数字可能过期了」。每一条当时都说过，**但它们散落在长对话里，用户翻不回去，而你不会主动回头收集**。

于是它们不是被拒绝，而是**被遗忘**——**这跟「做完了」在外观上毫无区别**。

**因此任何一次「交回给用户验收」的发言，都要带一张汇总清单**，不是只提最后一轮那条。交付前从会话开头扫一遍，把所有「等人确认」的条目收拢。清单要求：

- **跨轮次汇总**，不是最近一轮
- **每条写清「去哪、做什么、期望看到什么」**——用户不该为了验收再翻上文
- **标出来源**（tasks 编号 / 哪一轮的哪个建议），便于回查
- **分档**：阻塞交付的（不做不能归档）／ 可选复核的（只是建议）
- **已验的也列出来并附结论**，让清单是完整的而不是只剩残项

这条与「勾不许替别人补，没做就留空」是配套的：留空是诚实的，但**留空之后必须有人被告知它留空了**，否则诚实的留空和悄悄的遗漏最终等价。

## 记录

**坑和「我搞错了」不是一回事。** 判据只有一句：**换一个人来做同样的事，他还会中招吗？** 会 → 是坑。不会 → 那只是一次判断失误，留下**更正后的事实**，不要留「我曾经错过」的记录。把失误堆进坑的文件里，代价是真正的雷被稀释。

**如果失误暴露的是方法问题，把方法写成规则**——方法问题会重复发生。

**发现没定的事就记下来，不要默默假设一个答案继续做。**

**决定要写下来的三条判据**（同时成立才写）：难以回退、日后读者会问「为什么这么做」、当时有真实的备选。

**注释只许引用能回源核对的出处**：ADR 编号、坑的编号、文件全路径。**绝不许引用派活 prompt 里的临时编号**（「任务 E」「第 3 组的 2.1」）——prompt 是一次性的，注释留下的是死链。

## 断线

你随时可能断线。**每合入一批就更新一份 HANDOFF**，写清：停在哪、下一步固定要做的几件事、哪些约束只活在临时任务书里（那些目录随时会被清理）、**哪些事必须等用户拍板**。

判断标准：一个冷启动的人只读 HANDOFF，能不能接着干。
