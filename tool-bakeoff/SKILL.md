# 工具对比：怎么测才算数

凭印象选型会得到一份看起来公允、实则每一格都可疑的表。这份 skill 是一套**让结论
能被别人复核**的流程，来自 2026-08-22 一次真实的三方对比（结论是砍掉其中一个）。

---

## 一、先立基准，再碰工具

**用一个真实的、你已经解决过的问题当题目**，不要用玩具例子。玩具例子每个工具都能过，
区分不出任何东西。

**挑题的判据：它要横跨被测工具的能力分界线。** 上次那道题（一个下拉框展开后撑宽页面）
根因横跨 TSX 结构与 CSS 两层——正好能把"有调用图"和"有全文索引"这两种能力分开。
如果题目只落在所有工具的共同强项上，测了也白测。

---

## 二、完整度必须机械化打分 ⚠️

**你已经知道答案了，这会污染判断。** 你会不自觉地把工具给的模糊线索读成"它也答对了"。

处置：**动手前把正确答案拆成 N 条可勾选的事实，每条带出处（文件:行号）**，然后用
`grep` 到各工具的输出里逐条打勾——不靠阅读，不靠印象。

```bash
score() { f=$1
  grep -q "特征串1" $f && printf "F1✓ " || printf "F1✗ "
  ...
}
```

拆事实时挑**只有真正答对才会出现的特征串**。问一句：**"如果这个工具根本没找到这件事，
这个串会不会碰巧也出现？"** 会，就换一个串。

---

## 三、口径统一，否则数字全是噪音

上次踩到的三处，每一处都足以让结论反过来：

1. **剔除进程启动开销。** 三个 CLI 各跑三次 = 九次冷启动。同一批查询在单进程长连接下
   是 0.76s，拆成三次独立进程是 9.4s——**差 12 倍，全是外壳**。
   对 MCP 类工具，写个小脚本 initialize 一次、连发多个 `tools/call`。
2. **别在别的重活跑着的时候测。** 有一组"空闲态"数字是在另一个工具全量索引时量的，
   直接作废重测。
3. **字节数是 token 的合理代理**，但要量**真实调查会拉进上下文的那部分**，
   不是工具能吐出的全部。

---

## 四、给每个工具它最好的打法（否则是你在赢，不是它在输）

上一轮我给 A 工具的是默认参数，它拿了 4/7；开了 `include_content` 之后拿 6/7。
**如果就此收摊，结论会是错的。**

判据：**每报一个"它做不到"，先问一句"是不是我没给它对的参数"。** 翻一遍它的
`--help` 和 MCP schema，把每个工具的最优打法都跑一遍，然后**把不同打法作为独立行
列进表里**（默认 / 全力各一行），因为它们的成本天差地别。

### ⚠️ 参数被静默忽略，会伪装成"工具做不到"

真实踩到：CLI 的 flag 叫 `--content`，MCP 的参数叫 `include_content`。
我传了 `{"content": true}`，**不报错、不警告，返回体跟没传时一字不差**。
差点写下"这工具带不出源码"的错结论。

**处置：传参前用 `tools/list` 读真实 schema，别照着 `--help` 的 flag 名猜。
传了一个开关之后，先确认返回体真的变了**（比字节数、比首行），再谈它的效果。

---

## 五、把「能力边界」和「配置没开对」分开

这是最容易得出错误结论的一步。两者症状一样（查不到），处置天差地别。

- **配置问题**：能通过改参数/重建索引解决。上次 A 工具查中文恒返回 0 条，
  是分词模式没开对，开了就好——**这不是它的能力边界**。
- **能力边界**：调什么参数都没用。A 工具只有 11 种语法解析器，CSS 永远进不了图。

**验法：去数它的底层事实，别读它的文档。** 例如直接查图里有几个该类型的节点：

```
MATCH (n) WHERE n.file_path ENDS WITH '.css' RETURN labels(n), count(*)
```

答案是 2 个文件级节点、0 个选择器节点——**结论就此钉死，不用再争**。

### 推论也要验，别接受"理论上应该"

用户当时提了一个很合理的推论：「B 工具索引的文件类型更多，所以它的影响半径应该更全」。
**测下来是错的**：多索引的那部分只进了全文索引，**没有进图**，不参与影响传播。

判据：凡是"因为 X，所以 Y 应该也……"，**Y 要单独测**。索引覆盖 ≠ 图覆盖 ≠ 能力覆盖。

---

## 六、头对头验"卖点能力"，用同一个输入

要砍掉一个工具，必须证明**它的主打能力被覆盖了**——而不是"另一个也差不多"。

做法：挑一个双方都声称支持的核心能力，喂**同一个输入**，比**具体数字**。
上次是同一个符号的影响半径：一个报 35，另一个报 35，风险标注也一致。
**再用第三方事实校验**（grep 数出调用它的文件数，与两边都对得上）——
两个工具一起错的可能性，比一个工具错要低得多，但不是零。

---

## 七、结论要带成本，也要带"失去什么"

只列优势的对比表是推销，不是评估。至少还要有：

- **持有成本**：索引体积、重建耗时、是否会改写你的仓库文件
- **维护面**：这轮里它造成过几次真实事故
- **砍掉会失去什么** —— **如实列出，包括你觉得不重要的那些**，
  并对每一条问"过去半年用过吗"。上次那个"独占能力"（污点分析）
  查下来**一次都没用过**，这条比任何性能数字都更有说服力。

最后给一条**可执行的判据**交回决策者，而不是替他拍板：
「如果接下来半年不打算做 X，就砍」。

---

## 八、报告落盘，结论写进 commit message

对比结论半年后会被质疑（"当初为什么砍它？"）。把**测法、原始数字、以及被证伪的那个
推论**一起写进仓库文档，commit message 里说清**为什么**而不只是改了什么。
被证伪的推论尤其要留——它是下一个人最可能重新提出的那一个。
