# 实现：清单你定，变绿派出去

输入：一个已经有四份规格产物的在途变更。

分工只有一句话：**`@e2e` 用例的清单由你从规格里机械枚举并锁死，执行方只负责让它们变绿。**
清单的完整性是你唯一不能外包的东西——它便宜（数标签而已），而让用例变绿是最贵的体力活。
**全包等于自己给自己出考卷**，「断言全绿而名单不全」这个亏是反复吃过的。

## 第 1 步：枚举并锁死清单（不外包）

从这次变更的增量规格里，把所有带 `[@e2e]` 标签的 `#### Scenario:` 逐条抄出来，一条一行，
落进任务书。这份清单**只增不改**：agent 不许添、不许删、不许改写场景名。

配一道数量闸门：**`@e2e` 标签数 == e2e 用例数**。

e2e 用例标题带前缀绑定 Scenario：

```ts
test('[<capability>/<Scenario 名，逐字抄自这次变更的增量规格>] 其余描述', ...)
```

⚠️ **前缀能加的唯一条件：那条 `@e2e` Scenario 在匹配集合里。** 集合的定义在哪、由什么决定，
见【项目适配】——**那里指到哪份文件，就让 agent 去读哪份文件的原文，这里和任务书里都不许
复述**（复述的那份会漂，而漂了不报错）。任务书要写明不读的后果：拿不在集合里的 Scenario
当前缀，会被判成**孤儿用例、当场红**，哪怕它真实存在。

**既有的无前缀用例保持原样**，不要顺手补前缀——等它们覆盖的能力下次被某个变更修改时，
随那次的增量规格一起补。

闸门是**双向**匹配：每个 `@e2e` 场景都有用例、每个前缀都能找到同名场景。只做单向的话，
被改名的场景会留下孤儿用例——照跑、照绿，断的却是一个已经不存在的承诺。

## 第 2 步：组装任务书，派一个子 agent

**这活的失败会当场变红**（清单已锁死，agent 只需让它们绿，做错了测试自己会喊），所以
**用便宜快的通道就够**，不必上更强的推理模型。通道可换，**重要的是任务书写了什么，不是谁
来跑**——派活机制（任务书要件、白名单 bundle、发送命令、被杀之后怎么收）见 `orchestrating-agents`
的「派活」一节；用哪个模型（命令名、价格）见 `dispatch-dlaude` / `dispatch-glm`。

任务书的**通用要件**（本场可用工具、报告落盘路径、划死不许碰的、注释只许引用能回源核对的
出处、交付要求写成可检查的）不在这里重复，照 `orchestrating-agents`「任务书写什么」办。
下面只写**这个 skill 特有**的部分。

必须点名（冷启动的 agent 不点名就不读，用全路径）：

- 这次变更的任务清单与设计文件
- 这次变更的增量规格全部文件
- 【项目适配】里列出的那几份（匹配集合的出处、执行侧操作手册）
- **相关的坑**：拿本次改动的领域词（表名、模块名、指标名）去坑库 grep 一遍，命中的按全路径
  逐个点名。凭回忆点名时漏掉的那份往往正是最该读的那份——因为你记得住的都是你已经在想的。

任务书要写死的几条：

- **第 1 步那份清单原文照抄进去**，并写明只增不改
- 每条任务的验法测试名**必须真跑**，报告里贴**真实输出条数**
- 划死不许碰的，除了通用那几项，这里还要补上：**别的变更**、**规格主文件**（主规格只在归档
  时合并，实现阶段不动）
- 注释可引用的回源出处，在这里具体是：决策编号、Requirement/Scenario 名、坑编号、文件全路径

## 第 3 步：实现报告的四项

写 scratchpad，**不进仓库**；要求**边做边写**，并在**测试跑绿之后、收尾之前**就把主体写完
（长任务接近上限时会被杀，活干完了报告丢了——发生过三次）。

1. 改了哪些文件
2. 每条任务的验法测试名与**真实输出条数**（passed · failed · skipped）
3. `@e2e` 用例与 Scenario 的对应表
4. **候选坑**——执行方只报候选，写进坑库的权限只归主模型（判定与落盘走 `/recording-lessons`）

第 2 项的条数必须报，因为 **`14 did not run` 和 `14 passed` 不是一回事**。

## 第 4 步：自己复核，然后问用户要不要扫

**不要相信执行方的日志，声称跑通的自己跑一遍。** 判据是**你亲手跑出来的输出**与报告一致。

没有报告 = 先当作有半截注入没回滚：`git diff` 逐处过一遍，找那种「删掉一个调用」
「把 true 改成 false」的孤立改动。

然后**问一句**，不要自作主张跑：实现已落地，要跑一遍标签闸门和全量 e2e 吗？
（命令见【项目适配】。标签闸门这一步终于该绿了——双向匹配 + 数量闸门。）

改到用户看得见的东西时，e2e 之外还要对照项目的设计原型——布局与可用性的退化**不会有任何
测试变红**。

## 项目适配

换项目时**只改这一节**，正文一个字不用动。

| 要什么 | 本项目的值 |
|---|---|
| 匹配集合的出处（让 agent 读原文，不许复述） | `src/Web.Tests/ScenarioTagScanTests.cs` 的类文档 |
| 执行侧操作手册 | `docs/EXECUTOR.md` |
| 坑库 | `docs/pitfalls/P-<编号>-<slug>.md`（一条一文件） |
| 标签闸门 | `dotnet test --filter ScenarioTagScanTests` |
| 全量 e2e | `cd src/web-ui && bun run test:e2e` |
| 设计原型 | `prototype/observer-page-v6.html`（**以仓库里最新那一版为准**，旧版落后于已拍板的决策） |
