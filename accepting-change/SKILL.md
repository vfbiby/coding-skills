# 验收与回流

输入：一个已经实现完、有实现报告的变更。

验收和回流是**一件事**：回流只在验收跑出问题的那一刻发生，它的输入就是你手里那个失败现象。
所以这个 skill 一口气走完。

## 第 0 步：先问一次，之后全程沿用

四道防线里，**第三、四道不能外包**（注入实验和「复核报告」都是判断，派出去等于让报告自证）。
真正可选的只有第一、二道，而它们要不要派通常是同一个理由。所以**开头用 AskUserQuestion 问一次**：

> 第一、二道防线派子代理跑，还是你自己来？

问一次就够，四道各问一次是噪音。

## 四道防线：抓的东西各不相同

| 防线 | 抓什么 | 抓不到什么 |
|---|---|---|
| 一 · 逐条对照审查 | **该有的断言在不在** | 断言全对但用户点不动 |
| 二 · 真浏览器走一遍 | 做完的东西**有没有出口** | 逻辑正确性 |
| 三 · 注入实验 | 已有断言**钉不钉得住** | 没写的断言 |
| 四 · 自己复核 | 前三道报上来的结论真不真 | 三道都没查的地方 |

**一和三缺一不可，且互相替代不了**：注入实验查的是「已有断言钉不钉得住」，逐条对照查的是
「该有的断言在不在」——**没写的断言，注入的时候什么都不会红**。

顺序：一、二并行（可派），报告回来后做三、四，最后自己跑 `@e2e` 场景。

### 第一道：逐条对照审查（必做，只读）

拿 spec 逐条对照实现。**判据是实测出来的**：有一轮我自己做了四个注入实验、一个洞都没多找到，
而逐条对照报了两个、注入验证两个都是真的——其中一个是「分两笔付清」一条断言都没有，
把求和改成只累计第一笔，77 条测试一条都没红。

派出去时**绝不给写权限和构建工具**。理由不止是安全：**能改代码的审查者会顺手把问题改掉，
然后报告里写「已修复」**——你就同时失去了「这个洞原本有多深」和「自己做注入验证」的机会。

**任务书里必须写的六句刁钻话**（不写这些，换回来的是一份复述注释的读后感）：

1. **「名单从出处枚举，先报总数。」** 「spec 里各有几条 Requirement、几个 Scenario，把数字
   写在表前面。」——防的是名单本身不全，而手抄的名单**只覆盖抄的人当时想到的那几个**。
2. **「结论只许三选一：已实现且有断言钉住 / 已实现但没有断言 / 没实现。」** 中间那一类是
   最要紧的——代码对、没人看着。不给这三个格子，它会全写「已实现」。
3. **「凡断言『某处没问题』，也要明说『逐条核过，没找到』，不许留空。」** 留空和「查了没有」
   长得一模一样。
4. **「任务书里有没有句子与代码或既有决策冲突？给出文件:行号。」** 特别点名三类：
   「做错 X 会导致 Y」（Y 必须能从代码读出来）、「当前实现是 Z」、「A MUST NOT B」
   （代码里到底拦没拦）。
5. **给它一条已知的坑当引子，让它顺着找同形的。** 这一条回报最高：上面那两个洞里的第二个，
   正是「顺着这条已知的坑往下找，还有没有别处的产品校验被假件提前挡掉」问出来的。
   **孤立地问「有没有问题」得到的是空泛回答；给一个具体形状让它去匹配，得到的是新实例。**
6. **「报告先落盘，再补后面几问。」** 长任务接近上限会被杀——已经因此丢过三次报告。

### 第二道：真浏览器走一遍（改到用户看得见的东西时才做）

条件触发：纯后端的变更不做。它与第一道**并列**，不是二选一。

判据同样是实测出来的：有一天用户在浏览器上点出**五个**缺陷，当时全部单元与集成测试都是绿的
——账号显示「已接入」但数据永远不来、短链接建完点不开也复制不了、相邻按钮粘成一个词、
分享链接从任何账号进去都一样、四个接口在开发期 404。**五条全是「做完了但没出口」**：
规格写的是「系统 SHALL 做 X」，**没有一条管「X 做完之后有没有人能用上它」**。

要点：

- 用**项目自己的 Playwright（或等价的 e2e 装置）**。**不要用浏览器扩展类工具**——装扩展的
  确认框会一直挂到用户醒来。
- 任务书点名：**「你改到的每一处用户看得见的东西，都要有一条 e2e 用例走到它」**，
  并要求**贴真实输出的条数**（passed / failed / skipped）。
- ⚠️ **`14 did not run` 和 `14 passed` 不是一回事。** 只看「有没有 failed」会把「整个套件
  根本没跑」读成通过——有个套件就是这么哑了三周的。**要求报条数，就是为了让这件事没法糊过去。**
- ⚠️ **「每条 `@e2e` Scenario 都有用例」那道闸门顶替不了这一道。** 它保证不了**用例覆盖
  之外**的退化——布局粘连、可访问名、点不到的入口，**不会有任何测试变红**。项目里若有
  设计原型，前端改动先对照原型，并说明「哪里不一致、为什么」。

### 第三道：注入实验（自己做）

把实现**亲手改坏**，确认红的是你以为会红的那一条，再改回来。**注入面要收窄到被测的那一个
维度。**

⚠️ 被杀在「改坏」和「改回来」之间时，那处破坏**看起来和一处实现一模一样**。所以注入前先留
基线（提交，或把目录复制一份），并在结束时 `git diff` 逐处过一遍。

### 第四道：自己复核（唯一不能派的一道）

**不信实现者的日志，也不信审查者的日志。** 报告里也有说得过重的地方，判据仍然是拿第三道的
手法——**亲手把代码改坏，看红的是不是它说的那一条**。

## 跑 spec 的 `@e2e` 场景

四道走完，**只按 spec 的 `@e2e` 场景跑一遍**（用项目自己的 e2e 命令）。这是验收的正式动作，
前面四道是为它做准备。

## 回流：一句话判据

对每一个失败现象问：

> **这个失败现象，spec 里有没有一条 Scenario 描述了它的正确形态？**
>
> **有** → 回实现方（没做到已经写明的事）
> **没有** → 回写 spec 的那一方（spec 漏了这个场景）

### 有 → 定点修复，在本 skill 内闭环

**不要重走实现流程**：清单不变、四件套不变、Scenario 不变，重新枚举并锁死用例清单纯属浪费。
组装一份定点修复任务书：**哪一条 Scenario / 现在的实际行为是什么 / 期望是什么**，定位到具体
的 Requirement 或 task 编号。**禁止整体感觉类评语。**

⚠️ **派出去时冷启动，不要 `--resume` 回实现那个会话。** 「刚实现完」是错觉——中间隔着审查
防线跑完、你读报告、跑 e2e、判定回谁，十几分钟起步且夹着人类决策，缓存早凉了。实测过一次
续派：只跑了 46 turns，未命中输入却是那批里最高的 131 万 token，因为整份转录按未命中价
重算了一遍。续派真正便宜的只有一种情形——**agent 刚交活、你立刻追问**。

### 没有 → 先补 Scenario，再转手

**回写 spec 的那一方，每一次都必须先落一条新 Scenario**，不许口头描述完就让人去改。
这是最要紧的一类——「没写的断言，注入的时候什么都不会红」搬到了 e2e 层。

补 Scenario 走 `/writing-change`（把「要补哪条、为什么」交代清楚后转手）。
**这个 skill 不自己改 spec。**
